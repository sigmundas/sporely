
# Spore statistics and Parmasto-style species profiles

## Purpose

Sporely currently stores per-observation spore statistics mainly as a legacy literature-style string, for example:

`Spores: (11.0-)11.3-15.5(-16.2) x (7.0-)7.3-9.2(-9.4) um, Q = (1.4-)1.4-1.9(-2.0), Qm = 1.7, n = 195`

This is good for human display, but it is not a reliable data contract for species-level statistics or Parmasto-style matching. In particular, the legacy string contains `Qm`, but not real `Lm` or `Wm`, so the landing page cannot correctly compute species-level mean length or width.

The goal is to move to structured, observation-level spore summaries and then build species profiles from those summaries.

The core statistical rule is:

> The species profile must be based on unweighted observation/specimen means, not weighted pooling of individual spores.

A specimen/observation with 300 measured spores must not overpower another valid specimen/observation with 20 measured spores. Spore count is a quality/inclusion signal, not the default weight for the species mean.

This plan deliberately uses a table/column approach, not more string parsing.

---

## Statistical principles

### 1. Three-level model

Data should be treated hierarchically:

```text
individual spore measurements
→ observation/specimen summary
→ species profile
````

Each observation/specimen gets real measured values:

```text
Lm = arithmetic mean of length values for that observation
Wm = arithmetic mean of width values for that observation
Qm = arithmetic mean of individual length/width ratios for that observation
```

Species-level values are then based on observation summaries:

```text
species Lm = unweighted mean of observation Lm values
species Wm = unweighted mean of observation Wm values
species Qm = unweighted mean of observation Qm values
```

### 2. Do not use weighted species means

Do not calculate canonical species means as:

```text
sum(observation_mean * n_spores) / sum(n_spores)
```

That only describes an arbitrarily pooled spore sample. It does not describe the species in a Parmasto-style specimen-balanced sense.

Weighted/pooled values may be shown later as a clearly labelled secondary view, but they must not be the canonical species profile.

### 3. Do not estimate means from p05/p95 midpoints

Do not use:

```text
estimated_Lm = (length_p05 + length_p95) / 2
estimated_Wm = (width_p05 + width_p95) / 2
```

for species profiles or matching.

That may be acceptable only as a temporary display-only fallback, and must be labelled:

```text
mean_source = "estimated_from_range"
```

Estimated means must not enter Parmasto-style scoring.

### 4. Qm must be real

`Qm` should be:

```text
mean(length_i / width_i)
```

for paired length/width measurements.

It should not be derived as:

```text
Lm / Wm
```

Store both later if useful, but the biometric `Qm` should be the mean of individual Q values.

## Stage A — Define data contract

### Goal

Define a structured observation-level spore summary format that can be computed by `sporely-py`, synced to Supabase, exposed through public RPCs, and aggregated on `sporely-landing`.

### Data unit

The primary unit is:

```text
one observation/specimen under one measurement context
```

Most observations will have one context, but the schema should support multiple contexts because sample type, mount, stain, and contrast can matter.

Examples of contexts that should not be silently mixed:

```text
fresh vs dried
water vs KOH
DIC vs brightfield
stained vs unstained
```

### Proposed table

Create a cloud table:

```sql
public.observation_spore_summaries
```

Suggested columns:

```sql
id bigint generated by default as identity primary key,

observation_id bigint not null references public.observations(id) on delete cascade,
user_id uuid not null,

context_hash text not null,
context_json jsonb not null default '{}'::jsonb,

measurement_type text not null default 'spore',

sample_type text,
mount_reagent text,
stain_reagent text,
contrast_method text,

n_spores integer not null default 0,
n_paired integer not null default 0,
n_length integer not null default 0,
n_width integer not null default 0,

length_min_um double precision,
length_p05_um double precision,
length_mean_um double precision,
length_median_um double precision,
length_p95_um double precision,
length_max_um double precision,
length_sd_um double precision,

width_min_um double precision,
width_p05_um double precision,
width_mean_um double precision,
width_median_um double precision,
width_p95_um double precision,
width_max_um double precision,
width_sd_um double precision,

q_min double precision,
q_p05 double precision,
q_mean double precision,
q_median double precision,
q_p95 double precision,
q_max double precision,
q_sd double precision,

stats_version integer not null default 1,
computed_at timestamptz not null default now(),
source_app text,
source_app_version text,

created_at timestamptz not null default now(),
updated_at timestamptz not null default now(),

unique (observation_id, context_hash)
```

Optional later columns:

```sql
profile_eligible boolean
quality_flags jsonb
taxon_id bigint
species_key text
```

For now, profile eligibility can be computed in SQL/RPC using `n_paired` and non-null real means.

### Context hash

`context_hash` should be deterministic. It should be derived from normalized context fields, for example:

```json
{
  "measurement_type": "spore",
  "sample_type": "fresh",
  "mount_reagent": "water",
  "stain_reagent": null,
  "contrast_method": "dic"
}
```

Normalize strings before hashing:

```text
trim
lowercase
empty string → null
known aliases collapsed where possible
```

Acceptance:

* Table supports one or more summary rows per observation.
* Summary rows are keyed by `(observation_id, context_hash)`.
* Means are stored as numeric columns, not only JSON/string.
* Old `observations.spore_statistics` remains untouched for compatibility.

## Stage C — sporely-py local computation

### Goal

Compute real observation-level statistics from raw measurements in `sporely-py`.

### Requirements

In `sporely-py`, update the spore statistics computation so it produces both:

1. the legacy literature string, for human display/export;
2. structured summary rows, for cloud sync and species profiles.

Do not parse the legacy string to get structured values. Structured values must come from raw numeric measurements.

### Valid measurement rules

For L/W/Q summaries:

* Use only valid paired measurements where both length and width are present and positive.
* `q_i = length_i / width_i`.
* `q_mean = mean(q_i)`.
* `length_mean_um = mean(length_i)`.
* `width_mean_um = mean(width_i)`.

For length-only or width-only values:

* `n_length` and length stats may be computed from all valid length measurements.
* `n_width` and width stats may be computed from all valid width measurements.
* But `n_paired` is the main eligibility count for species profile and matching.

### Percentiles

Use the same percentile convention currently used for the legacy string, unless there is a strong reason to change it.

Document whether p05/p95 are:

```text
nearest-rank
linear interpolation
numpy percentile default
custom existing method
```

Do not silently change percentile behavior without updating tests.

### Standard deviation

Use sample standard deviation where appropriate:

```text
sd = sqrt(sum((x - mean)^2) / (n - 1))
```

If `n < 2`, `sd = null`.

### Context grouping

Initially, group measurements by normalized context:

```text
measurement_type
sample_type
mount_reagent
stain_reagent
contrast_method
```

The context source should come from the image/measurement metadata already used for the public plot filters.

If a measurement lacks context, use null fields and include it in a null-context summary.

Acceptance:

* `sporely-py` can compute real Lm/Wm/Qm from raw measurements.
* Legacy string still works.
* Structured summaries are deterministic.
* Multiple contexts in one observation produce multiple summary rows.
* No midpoint-estimated means are generated as real means.

## Stage D — sporely-py local schema and sync

### Goal

Persist computed summaries locally and sync them to Supabase.

### Local persistence

Add a local table or cache representation mirroring the cloud table enough for sync:

```text
observation_id
context_hash
context_json
n_paired
length_mean_um
width_mean_um
q_mean
...
computed_at
stats_version
```

This may be a proper local table or a deterministic computed payload generated during sync, but a local table is preferable for debugging and performance.

### Sync behavior

During cloud sync:

1. Ensure observation exists remotely.
2. Compute or load current observation summary rows.
3. Upsert to `public.observation_spore_summaries` by:

   ```text
   observation_id + context_hash
   ```
4. Delete remote summary rows for that observation/context that no longer exist locally, or mark stale if deletion is risky.
5. Do not sync midpoint-estimated means.
6. If the cloud table does not exist yet, fail gracefully or skip with a clear compatibility warning.

### Desktop compatibility

The cloud migration must be deployed before a desktop release that writes to this table.

Acceptance:

* New/edited spore measurements update summary rows.
* Deleting measurements updates or removes affected summary rows.
* Sync is idempotent.
* Re-running sync does not duplicate rows.
* Existing observations backfill on next desktop sync.

## Stage G — Species aggregation

### Goal

Replace weighted pooling with observation-balanced species profiles.

### Canonical aggregation

Given eligible observation summaries:

```text
m = number of eligible observation summary rows
u = number of contributors
N = sum(n_paired)
```

Compute:

```text
grand_Lm = arithmetic mean(length_mean_um over observation summaries)
grand_Wm = arithmetic mean(width_mean_um over observation summaries)
grand_Qm = arithmetic mean(q_mean over observation summaries)
```

Compute between-observation spread:

```text
sd_Lm = sample standard deviation of observation length_mean_um
sd_Wm = sample standard deviation of observation width_mean_um
sd_Qm = sample standard deviation of observation q_mean
```

If `m < 2`, SD values are null/provisional.

### Contributor-balanced diagnostic

Also compute contributor-balanced values internally:

```text
per_contributor_Lm = mean(length_mean_um for that contributor)
contributor_balanced_Lm = mean(per_contributor_Lm)
```

Do this for L/W/Q.

Initially this can be used only for diagnostics. Later the UI can warn when one contributor dominates.

### Dominance diagnostics

Compute:

```text
largest_contributor_observation_count
largest_contributor_fraction
```

Potential warning:

```text
Profile is dominated by one contributor; species mean is provisional.
```

### Display

Species profile should show:

```text
Lm / Wm / Qm grand means
SD of observation means
number of observations
number of contributors
total paired spores
filters applied
profile status
```

Profile status examples:

```text
insufficient data: m < 3
provisional: m >= 3 but u < 2
community-supported: m >= 10 and u >= 3
strong: m >= 25 and u >= 5
```

Exact thresholds can be changed later.

Acceptance:

* `poolSporeSummaries` no longer uses spore-count-weighted means for canonical species means.
* The default species profile is observation-balanced.
* The UI reports observation count, contributor count, and total spores.
* Contributor dominance can be detected.

## Stage I — Parmasto-style matching foundation

### Goal

Prepare for ID assistance without implementing a full black-box matcher yet.

### Input

A query observation must have a real measured summary:

```text
query_Lm
query_Wm
query_Qm
query_n_paired
```

Do not match from midpoint-estimated means.

### Basic transparent score later

First version can use separate standardized deviations:

```text
zL = (query_Lm - grand_Lm) / max(sd_Lm, minimum_L_tolerance)
zW = (query_Wm - grand_Wm) / max(sd_Wm, minimum_W_tolerance)
zQ = (query_Qm - grand_Qm) / max(sd_Qm, minimum_Q_tolerance)
```

Then:

```text
distance = sqrt(zL² + zW² + zQ²)
```

Later improvement:

```text
Mahalanobis distance using covariance of observation means
```

Do not use SEM alone for matching. SEM becomes too small as the database grows and would make the matcher falsely strict. Matching should use biological between-observation spread.

### Tolerance intervals

Tolerance intervals may be added later:

```text
grand mean ± k * sd
```

But `k` must be chosen for a defined coverage/confidence level and enough observations. For small sample counts, label all intervals provisional.

Acceptance for this stage:

* Data needed for matching exists.
* No fake means are used.
* Species profile exposes between-observation SD.
* Match explanations can eventually say which dimension fits or fails.

## Stage K — Rollout plan

### Step 1: schema first

Deploy Supabase migration before releasing clients that write the new table.

### Step 2: desktop writer

Release `sporely-py` support for computing and syncing structured summaries.

Existing observations are backfilled on next sync.

### Step 3: landing reader

Update `sporely-landing` to read structured summaries and aggregate observation-balanced species profiles.

### Step 4: remove weighted canonical means

Any current species-level weighted mean logic should either be removed or renamed:

```text
pooled_individual_spore_mean
```

It must not be labelled as the species mean.

### Step 5: matching later

Do not implement Parmasto-style matching until enough structured summaries exist and the profile UI is stable.

## Non-goals for the first implementation

Do not implement full ID scoring yet.

Do not implement covariance/Mahalanobis matching yet.

Do not use midpoint-estimated means for species profiles.

Do not remove the legacy `spore_statistics` string.

Do not try to clean all historical rows in one migration. Let desktop sync backfill structured summaries from raw data where available.

Do not treat total spore count as a weight for the canonical species mean.

## Final target

The intended long-term architecture is:

```text
raw measurements stay raw
observation summaries are computed from raw measurements
species profiles are computed from observation summaries
Parmasto matching compares one observation summary against species profiles
```

Canonical species-level means are unweighted means of observation/specimen means.

Spore counts are used for quality thresholds and transparency, not as species-profile weights.

### Key facts confirmed

- **No local or cloud table currently stores structured per-observation L/W/Q means.** They are computed on demand (Python `numpy` locally; PL/pgSQL lateral joins remotely) each time. That is the gap this plan closes.
- **Measurement context does not live on `spore_measurements`.** It lives on the parent `observation_images` / `images` row (`mount_medium`, `stain`, `sample_type`, `contrast`). Each raw measurement → one image → its image-level context. This is authoritative for Stage C context grouping.
- **Observation-level context is not stored anywhere in the current schema.** An observation with multiple microscope images can already have per-image differing context; the summary table must therefore key by `(observation_id, context_hash)`, exactly as the plan proposes.
- **Existing RPC surface already uses the plan's public names.** `p_mount_reagent`, `p_contrast_method`, `p_sample_type` are the query-parameter spellings even though the underlying image columns are `mount_medium`, `stain`, `contrast`. That gives us an anchor for column naming (see open decisions).

Aligns with the plan's suggested table with three deliberate deviations, all justified by existing code:

create table public.observation_spore_summaries (

### Context normalization design

Normalization pipeline for each context field before hashing (executed in sporely-py Stage C, and mirrored in any SQL-side helper if we need one):

1. Coerce to `str` (from possibly None / int / bool).
2. `strip()`.
3. `casefold()` (lowercase; casefold is friendlier for accented characters than `.lower()`).
4. Collapse internal whitespace to single spaces.
5. If empty string → `None`.
6. Apply the alias table below.

Alias table — derived from the existing default lists in `sporely-py/database/schema.py:41,51,60` and from what the landing filters accept:

```text
mount_reagent:
  'h2o' | 'water (h2o)'           -> 'water'
  'koh 3%' | 'koh 5%' | 'koh 10%' -> 'koh'
  'nh4oh'                         -> 'ammonia'
  'melzer' | 'melzer\'s'          -> 'melzer'   # some users record stain here
stain_reagent:
  'congo red' | 'congo_red'       -> 'congo red'
  'melzer' | 'melzer\'s reagent'  -> 'melzer'
  'phloxine b'                    -> 'phloxine'
contrast_method:
  'bf' | 'brightfield' | 'bright field' -> 'brightfield'
  'dic' | 'nomarski'              -> 'dic'
  'phase' | 'phase contrast' | 'ph' -> 'phase'
sample_type:
  'fresh' | 'live'                -> 'fresh'
  'dried' | 'dry' | 'exsiccate' | 'exsiccatum' -> 'dried'
  'rehydrated' | 'rehyd'          -> 'rehydrated'
measurement_type:
  'spore' | 'spores' | 'basidiospore' -> 'spore'
```

Alias table is deliberately conservative in Stage A — Stage C will pin the exact list once we've grepped user-facing values in `lab_metadata` and existing observation rows. New unknown values pass through unchanged after steps 1-5.

**Context object** (canonical shape for JSON serialization before hashing) is a plain dict with keys in this fixed order:

```text
measurement_type, sample_type, mount_reagent, stain_reagent, contrast_method
```

Missing values are represented as JSON `null`. Serialization uses `json.dumps(context, separators=(',', ':'), sort_keys=True, ensure_ascii=False)`. Hash is `sha256(serialized.encode('utf-8')).hexdigest()`. Store the full hex (64 chars) in `context_hash`; index it as-is.

The identical canonical object goes into `context_json` for debugging / RPC exposure.

**Context source — resolved.** Context comes from `observation_images` (cloud) / `images` (local), joined via `spore_measurements.image_id`. Field mapping:

```text
sample_type      <- observation_images.sample_type      (normalize + alias)
mount_reagent    <- observation_images.mount_medium     (normalize + alias)
stain_reagent    <- observation_images.stain            (normalize + alias)
contrast_method  <- observation_images.contrast         (normalize + alias)
measurement_type <- spore_measurements.measurement_type; if 'manual' fall back to
                    observation_images.micro_category ('Spores' -> 'spore', etc.);
                    default 'spore' when both are empty.
```

**What Stage C does if context cannot be reliably assigned per measurement.**
The join above is always defined (every `spore_measurements` row has an `image_id`), so per-measurement context is always available in principle. However, current data will have many null/blank image context fields. Least-risky Stage C behavior:

- Group any measurement whose image context has all four prep fields blank into a single "null-context" summary row with `context_json = {"measurement_type": "spore", "sample_type": null, "mount_reagent": null, "stain_reagent": null, "contrast_method": null}` and its deterministic hash.
- Do NOT try to fabricate context from `lab_metadata` in Stage C. Defer that to a later stage after Stage F is stable.
- Emit one summary row per distinct normalized context that actually occurs for the observation. Never split further (e.g. never by objective_name) in this stage.

### Eligibility rules draft (informational — not implemented yet)

canonical_species_profile_eligible(row) :=

### Open decisions (please decide before Stage B)

### How context is linked from measurement to image

Per Stage A: `spore_measurements` has no context columns; context lives on the parent `images` row (`mount_medium`, `stain`, `sample_type`, `contrast`). The Stage C loader joins on `m.image_id = i.id` and injects those columns into each measurement row. The compute function reads them via `_row_context()`, which:

- Prefers the summary-facing names (`mount_reagent`, `stain_reagent`, `contrast_method`, `sample_type`) if present on the row (so Stage D and tests can pass pre-mapped rows), then falls back to the image-column names (`mount_medium`, `stain`, `contrast`). Verified by `test_summary_field_names_win_over_image_column_names`.
- Sets summary `measurement_type` to `'spore'` for every group (this is the *summary* type, not the raw-row provenance). The raw row's `measurement_type` field is only used to *filter* which rows count — matching the legacy filter set `{None, '', 'manual', 'spore', 'spores'}`. Non-spore rows (`basidium`, `cystidium`, ...) are dropped entirely; they will be handled by future non-spore summary types, not by this stage.

Every row's context is always defined (images always have the four fields, even if all four are NULL). Rows whose image context is fully NULL land in the single "null-context" summary row for that observation, per the Stage A least-risky policy.

### Percentile convention

`numpy.percentile(x, [5, 50, 95])` — numpy default linear interpolation. This exactly matches the legacy literature-string generator (`np.percentile(x, 5)` / `np.percentile(x, 95)` in `MeasurementDB.get_statistics_for_observation`), so the new structured Lm/Wm/Qm and the legacy display string cannot disagree on min/p05/median/p95/max.

Documented in the module docstring and pinned by `test_percentile_convention_is_numpy_linear_interpolation` (uses the known values for `[1..10]`: p05=1.45, p50=5.5, p95=9.55).

### Standard deviation convention

**Deliberate departure from legacy.** Legacy `np.std(x)` is *population* SD (ddof=0). The new structured summary uses *sample* SD (ddof=1) per the Stage C plan, with `sd = None` when `n < 2`.

The legacy literature string still uses population SD internally, but the legacy string does not surface an `sd` value directly (it prints min/p05/p95/max), so there is no visible behavior change from this departure. Documented in the module docstring and covered by `test_sample_sd_is_none_for_single_value_and_ddof1_for_more`.

### Legacy string generation — left parallel

Stage C created the structured computation path in parallel. The legacy `_format_measurement_stats_string()` still calls `MeasurementDB.get_statistics_for_observation()` (population SD, `count` = length count, etc.). Rewiring the legacy string to call `compute_observation_spore_summaries` would change:

- SD convention (population → sample) — irrelevant to the printed string but observable via other callers of `get_statistics_for_observation`.
- The `count` field semantics (legacy `count = len(lengths)`, new `n_spores = raw row count`).

Both are subtle behavior changes for a display-only compatibility surface. Stage C spec says: *"If this risks changing behavior, keep the legacy path untouched for now and document that Stage C created the structured computation path in parallel."* → done.

## Stage C — patch progress note (2026-07-12)

**Status: done.** Two Stage C defects fixed in place: the context-hash serialization order and the Lm/Wm/Qm denominator.

### 1. Context serialization order — fixed

Previous Stage C code called `json.dumps(payload, sort_keys=True, ...)` and claimed in a comment that "the five CONTEXT_KEYS happen to sort into the same fixed order." That claim was wrong. Alphabetical order of the five keys is:

```
contrast_method, measurement_type, mount_reagent, sample_type, stain_reagent
```

vs. the plan's fixed CONTEXT_KEYS order:

```
measurement_type, sample_type, mount_reagent, stain_reagent, contrast_method
```

`utils/spore_summary.py::serialize_context` now uses `sort_keys=False` and builds the payload by iterating `CONTEXT_KEYS`. Passing any Mapping is safe: caller-side dict ordering does not affect the hash because we rebuild the payload in CONTEXT_KEYS order ourselves. The docstring explicitly warns not to switch back to `sort_keys=True` since the resulting string is deliberately non-alphabetical.

The wire contract is therefore now:

```
{"measurement_type":"spore","sample_type":null,"mount_reagent":"water","stain_reagent":null,"contrast_method":"dic"}
```

### 2. Paired-denominator canonical means — fixed

Previous Stage C code computed `length_min_um / p05 / mean / median / p95 / max / sd` from **all** valid positive length values and `width_*` from **all** valid positive width values, while `q_*` used only paired rows. That let Lm, Wm, and Qm come from different denominators whenever length-only or width-only rows existed.

`utils/spore_summary.py::_summary_row_from_group` now feeds `_percentile_bundle` from `paired_lengths` and `paired_widths` (and `ratios` unchanged). All three canonical bundles share one paired-row denominator, matching the Parmasto-style intent.

Transparency counters are unchanged:

- `n_spores` — raw eligible spore-row count in the context group.
- `n_paired` — count of rows with both length and width valid.
- `n_length` — count of rows with valid positive length (paired + length-only).
- `n_width` — count of rows with valid positive width (paired + width-only).

Length-only and width-only descriptive stats are *not* added as new columns here. If we later want them, that is a schema extension for a future stage, not something to smuggle into the canonical fields.
