## Principles

Four things stay separate:

1. **Sporely concept identity.** Immutable `sporely_taxon_id`, allocated only
   by the registry, bound only by reviewed, evidenced reconciliation.
2. **Canonical nomenclature.** The COL-backed `canonical_scientific_name`.
3. **National nomenclature.** Preferred Norwegian/Swedish scientific names and
   vernaculars by language. Display and search metadata, never identity.
4. **Provider and publishing identities.** NorTaxa, Artsorakel raw ids and
   name snapshots, Dyntaxa, Artportalen, iNaturalist. Always namespaced, always
   provenance-preserving.

A name may suggest a reconciliation candidate. A name alone never proves one.
Exact scientific-name or authorship agreement never becomes automatic
cross-source identity (`identity-contract.md`,
`mapping_policy.continuity_rules.canonical_name_only`).

## Approved decisions (2026-09-27)

1. Group A (bridge coverage) goes before Group B (duplicate candidates).
2. Batch approval is allowed only for an explicitly enumerated, immutable
   candidate manifest. One review decision may approve the whole manifest, but
   it must produce an auditable per-association mapping for every member,
   pinned to the source releases it was reviewed against. It is never an
   evergreen rule that approves new taxa in a later source release. Evidence
   handling:
   - `reciprocal_accepted_synonymy`: strongest batch-review candidate;
   - `shared_synonymy`: batch evidence and statistics prepared for review;
   - `one_directional_accepted_synonymy`: individual review;
   - `no_published_cross_reference`: stays unresolved.
   The fail-closed bridge-emission architecture is preserved.
3. After new Group-A bridges are active, an explicit, idempotent repair pass
   re-resolves historical cloud `external_unresolved` observations, from
   preserved source + namespace + external id only. The owner does not have to
   open the observation.
4. Norwegian scientific display uses the approved NorTaxa preferred name when
   an approved NorTaxa identity exists; otherwise canonical COL. Canonical
   identity and canonical name never change. Search accepts both names.
5. Sweden follows the same architecture later: Dyntaxa preferred scientific
   name and Swedish vernaculars layered on the same Sporely identity. Dyntaxa
   is openly available (SLU Taxon Service API and Darwin Core download; the
   SLU checklist on GBIF is CC0 1.0), but the stage must pin, fingerprint and
   verify the actual archive and record its exact licence and citation.
6. Group-B work is "reconcile duplicate candidates", not "merge duplicates".
7. Stage order is as below.
8. National display fields are added alongside `canonical_scientific_name`;
   no schema bump unless additive is impossible.

**Group B — duplicate candidates.** A NorTaxa concept and a COL concept share a

Rules of the gate:

- Approval binds `file_sha256`, not `members_sha256` alone.
- It is bound to the pinned release, source and policy inputs above.
- Approving a child review manifest does not approve the parent
  `shared_synonymy` manifest, any sibling review class, a regenerated manifest
  with a different `file_sha256` (even with the same members), or any later
  source release.
- Stage 1A generates mappings only for members of the owner-confirmed
  manifest. Before generating, it verifies that the manifest file's SHA-256
  equals the confirmed `file_sha256` and that its `pins` equal the inputs
  above, and stops if either differs.
- Any further manifest needs its own explicit owner decision recorded here
  before a stage may consume it.

Scope:

- Generate one per-association reviewed mapping per member of the
  owner-confirmed manifest, carrying the existing required fields
  (`reviewer`, `rationale`, `evidence_references`, `source_release_range`, and
  so on) and a reference to the approved manifest's `file_sha256`. The
  implementer chooses where the records live (inline in `manual_mappings.yml` or in a batch file the same loader
  validates), records the rationale in the stage notes, and the stage review
  judges that choice.
- `bridge_emission.py` emits only approved records with complete provenance,
  as today. Nothing is emitted from an evidence class alone.

Acceptance gate:

- Every emitted bridge traces to a per-association record and the
  owner-confirmed `file_sha256`.
- A candidate that is not in the owner-confirmed manifest is never emitted,
  including a member of any unapproved sibling review class and a new taxon
  introduced by a later NorTaxa release (test with a synthetic additional
  source row).
- `no_published_cross_reference` associations stay unemitted.
- No `sporely_taxon_id` changes; the registry is untouched.
- NorTaxa 56227 (Craterellus tubaeformis → 620306) stays unresolved after
  Stage 1A. That is intentional and is not a Stage 1A regression: it is
  `single_shared_synonym_low_overlap`, which the owner did not approve. Its

- Regressions: 53482 → 7821 and 52369 → 83668 unchanged; an `ordinary`

  Dyntaxa namespace, from the export fixture Stage 4P produces.
- Swedish display needs no new web work beyond Stage 3W; this stage only
  adds a regression that the Stage 4P Swedish names reach the web label.

Acceptance gate:

- A reviewed Dyntaxa id resolves to its concept; an automatic, unknown or
  ambiguous one stays unresolved; no resolution from name text.
- Existing NorTaxa/COL resolution is unchanged.
- Regressions (web): a concept that Stage 4P gives a Swedish preferred
  scientific name or vernacular shows it in Swedish; one it does not still
  falls back to canonical COL.

## Stage 5 — Web and Android presentation follow-ups

Repos: sporely-web (Android is the Capacitor shell of the same code). Can run
in parallel with Stages 1A–4W.

Scope:

- Kraghätting: enable the `sporely-debug-artsorakel` snapshot, reproduce the
  NBIC:58766 suggestion, capture the raw candidate, and determine whether
  Artsorakel omitted the scientific name or the normalizer missed its field.
  No code change before the payload is captured.
- Decide whether Finds should indicate that an observation is
  `external_unresolved`. The implementer proposes the decision with its
  rationale and the stage review judges it.

Acceptance gate:

- The Kraghätting mechanism is proven from the captured payload before any fix.
- Any label fix does not change identity handling.
- The Finds decision is recorded with its rationale in sporely-web
  `docs/taxonomy-v2-cloud-contract.md`, whether or not it changes the UI. If
  it adds an indicator, focused presentation tests cover it and identity state
  is unchanged.

## Stage 6P — Deterministic release and regression proof

Repos: sporely-py (build, bundle, probes).

Scope:

- Build with `build_release.py` twice and require byte-identical output.
- Extend `tests/test_taxonomy_release_probes.py` with the regression table.
- Update `cloud_export` `PINNED_RELEASE_EXPECTATIONS` and produce the scoped
  export, with its fingerprints, for Stage 6W.

Acceptance gate:

- Deterministic double build; all probes and compatibility checks pass.
- The release delta lists only approved bridges, supersessions and display
  fields. No Sporely id is allocated or changed except by an approved
  supersession; in particular no Dyntaxa-only concept is allocated (Stage 4P
  scope).

## Stage 6W — Production import package for the new release

Repos: sporely-web. The accepted Stage 6P sporely-py candidate is pinned as a
sibling and not modified. Prepare only; nothing runs against production.

Scope, as for earlier releases (for example the `tax-2026.09.23-01` import
preparation and the `tax-2026.09.26-02` transition runbook):

- Prepare the production import payload from the pinned Stage 6P scoped
  export with `prepare-production-release-import.mjs`, pinned to its release
  id and fingerprints.
- Write the release-transition runbook: import, activation, post-activation
  probes for the regression table, rollback, and the Stage 1B dry run and
  repair steps that follow activation.

Acceptance gate:

- The payload builds from the pinned export and its fingerprints match
  Stage 6P.
- The runbook's probes cover the regression table.
- No production state changes.

## Production steps after Stage 6W

Each step needs its own explicit go-ahead and runs from the Stage 6W runbook.
None is an implementation stage.

1. Import and activate the Stage 6P release. Before any supersession ships,
   repeat the Stage 2 read-only check that no cloud observation references a
   retiring concept.
2. Stage 1B production dry run against the active release, with its report of
   exactly the rows that would change. It mutates nothing.
3. Stage 1B production repair of exactly the dry-run set, then the post-run
   audit report and a second run proving it changes nothing.
