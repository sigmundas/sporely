## Principles

Four things stay separate:

1. **Sporely concept identity.** Immutable `sporely_taxon_id`, allocated only
   by the registry, bound only by reviewed, evidenced reconciliation.
2. **Canonical nomenclature.** The COL-backed `canonical_scientific_name`.
3. **National nomenclature.** Preferred Norwegian/Swedish scientific names and
   vernaculars by language. Display and search metadata, never identity.
4. **Provider and publishing identities.** NorTaxa, Artsorakel raw ids and
   name snapshots, Dyntaxa, Artportalen, iNaturalist. Always namespaced, always
   provenance-preserving.

A name may suggest a reconciliation candidate. A name alone never proves one.
Exact scientific-name or authorship agreement never becomes automatic
cross-source identity (`identity-contract.md`,
`mapping_policy.continuity_rules.canonical_name_only`).

## Approved decisions (2026-09-27)

1. Group A (bridge coverage) goes before Group B (duplicate candidates).
2. Batch approval is allowed only for an explicitly enumerated, immutable
   candidate manifest. One review decision may approve the whole manifest, but
   it must produce an auditable per-association mapping for every member,
   pinned to the source releases it was reviewed against. It is never an
   evergreen rule that approves new taxa in a later source release. Evidence
   handling:
   - `reciprocal_accepted_synonymy`: strongest batch-review candidate;
   - `shared_synonymy`: batch evidence and statistics prepared for review;
   - `one_directional_accepted_synonymy`: individual review;
   - `no_published_cross_reference`: stays unresolved.
   The fail-closed bridge-emission architecture is preserved.
3. After new Group-A bridges are active, an explicit, idempotent repair pass
   re-resolves historical cloud `external_unresolved` observations, from
   preserved source + namespace + external id only. The owner does not have to
   open the observation.
4. Norwegian scientific display uses the approved NorTaxa preferred name when
   an approved NorTaxa identity exists; otherwise canonical COL. Canonical
   identity and canonical name never change. Search accepts both names.
5. Sweden follows the same architecture later: Dyntaxa preferred scientific
   name and Swedish vernaculars layered on the same Sporely identity. Dyntaxa
   is openly available (SLU Taxon Service API and Darwin Core download; the
   SLU checklist on GBIF is CC0 1.0), but the stage must pin, fingerprint and
   verify the actual archive and record its exact licence and citation.
6. Group-B work is "reconcile duplicate candidates", not "merge duplicates".
7. Stage order is as below.
8. National display fields are added alongside `canonical_scientific_name`;
   no schema bump unless additive is impossible.

## Stage 3R — Release-build inputs follow concept supersessions

Repos: sporely-py. Depends on Stage 3P. Must be accepted before Stage 4P,
Stage 6P and any other stage that runs `build_release.py` or
`build_sqlite_candidate.py` over the committed release recipe.

Root cause: Stage 2 retired concepts through `concept_supersessions.yml`, but
the pinned downstream build inputs still key entries to the retired
`sporely_taxon_id`s. The diagnostic count is 20 entries in
`sources/inaturalist_refresh/2026-09-26/inaturalist-refresh.json`, the first
one hit being 622141 Hymenochaete mougeotii, and 1 in
`overlays/artportalen-publishing.json` (624588 Amanita muscaria).
`build_sqlite_candidate.py` refuses each one ("concept … is not in this
release"), so the committed recipe cannot build a release from the branch.

Scope:

- When a pinned overlay or refresh entry references a concept that the
  registry records as superseded, the build re-keys it to the surviving
  concept, following the recorded supersession, and does not reinterpret any
  external identifier.
- The re-keyed row keeps its provenance: the original retired
  `sporely_taxon_id` and the `supersession_id` that moved it, in the build
  output and its report.
- The build fails when the retired and the surviving concept both carry
  conflicting entries for the same input, and still fails on an id that is
  neither in the release nor recorded as superseded.
- The release-recipe preflight in `build_release.py` reports every pinned-input
  reference to a superseded concept, and fails on any that cannot be resolved,
  before normalization and compilation start.
- The pinned input files stay byte-identical and keep their recorded
  fingerprints; the repair happens at build time.
- Recount the affected entries from the committed inputs and record them in
  the stage evidence; the numbers above are from the diagnostic build only.

Acceptance gate:

- Focused tests: a superseded entry re-keys successfully; its provenance
  survives into the output; a retired-plus-survivor collision fails; an
  unknown id fails; the release-recipe preflight catches an unresolved
  superseded reference.
- `build_release.py` over the committed recipe completes into a scratch build
  directory, without `--promote`. Nothing is promoted into the desktop bundle
  in this stage.
- No Sporely id is allocated or changed; no identity, canonical name or
  approved relationship changes. The only difference in output is the
  re-keying of the entries the preflight lists.
